## A 组 · 总纲与架构

### D1 · 全面转生产级：内存字典 → PostgreSQL + Alembic，业务逻辑平移不重写

- **背景**：demo 版全部数据存 Python dict（store.py），重启即清空，是"4 天验证闭环"的故意取舍；v1.0 转生产级后第一刀就是换库。
- **决策**：M1 全量迁 PG（SQLAlchemy 2.0 + Alembic 迁移）；**已验证的业务逻辑（状态机/双时刻/免登录/双轨素材）只平移不重写**。
- **为什么当初敢用内存库**：4 天交付期里，"验证业务流程对不对"的风险远大于"数据会不会丢"；换库成本被人为压到最低。
- **为什么现在迁移成本低**：demo 阶段就把所有读写**收口在 store.py 单模块**（没有任何路由直接摸数据）——当初收口就是为今天换库留的口，路由层 28 个接口几乎不动。
- **放弃的备选**：MySQL（团队无偏好差异，PG 的 JSONB 承载 command.payload 更顺）、MongoDB（事务与关系约束弱，指令队列需要强一致）。

### D2 · Redis 是加速层，不是事实源；挂了降级不 fail-closed

- **决策**：Redis 只承担三件事——长轮询唤醒 pub/sub（指令送达 ≤5s）、日程/在线状态缓存、调度图分布式锁。**指令队列唯一事实源是 PG 的 command 表**。
- **为什么**：Redis 抖 10 秒不能让设备收不到指令——pub/sub 不可用时设备长轮询超时后自然重查 PG 队列，退化为"纯轮询"模式，只是变慢不是变坏。
- **放弃的备选**：Redis Streams 当主队列（多一层持久化心智，PG 已够）；RabbitMQ/Kafka（单项目体量过度设计，Kafka 留给真·高吞吐场景）。
- **原则沉淀**：加速层挂了 = 退化到慢速正确路径，绝不能 = 功能不可用。

### D3 · Milvus 向量同理：加速层不是事实源，PG 先写、Milvus 后写

- **决策**：素材/知识库本体与元数据落 PG，向量化**异步**执行；写入顺序 PG 事务 commit 成功后才写 Milvus；向量化失败返回 2013（本体已保存，可重试补向量）。
- **为什么**：向量可从 PG 全量再生；反过来会产生"向量库有、事实库无"的孤儿数据，检索出幽灵素材排查困难。
- **为什么向量失败不算上传失败**：搜图是增强体验，不是素材存在的必要条件——阻断上传等于让次要依赖绑架主链路。

### D4 · 编排边界：LangGraph 管确定性调度，CrewAI 只管内容生成

- **决策**：服务端调度 pipeline（日历→状态机→指令生成）用 **LangGraph 状态图**（APScheduler 定时唤起，checkpointer 落 PG）；文案生成/选版式用 **CrewAI crew**（Agent A 文案 + Agent B 选版式）；两者通过 store/PG 交接，不互相嵌套。
- **为什么调度不用 LLM**：调度是 90% 的确定性逻辑，塞 Agent 是过度设计且引入不可控；状态图化换来的回报是**可观测、可回放、断点续跑**（每次图执行可审计）。
- **为什么内容生成用 CrewAI 而非 LangGraph 单图**：文案+选版式天然是"多角色协作"（写手+审版式），CrewAI 的角色/工具模型贴合；LangGraph 单图也能做但角色语义弱。
- **放弃的备选**：全走 LangGraph（少一个依赖，但多角色协作表达别扭）；全走 CrewAI（确定性调度会混进 LLM 不确定性，红线）。

### D5 · 多实例部署口径：接口无状态可横向扩，调度图单实例执行

- **决策**：uvicorn worker 可多开；LangGraph 调度图用 **Redis 分布式锁**保证同一时刻只有一个实例执行。
- **为什么**：调度图重复执行会造成重复入队/重复发邮件，幂等键只能兜指令不能兜邮件（邮件没有 command_id）。锁是最便宜的防重。

## B 组 · 调度与协议（demo 已验证，平移的决策）

### D6 · 双时刻 prepare_at / switch_at，自动切换唯一路径 = 设备本地定时

- **决策**：PREPARE_MEETING 携带两个时刻——prepare_at（会前 10min，预拉取）、switch_at（会前 1min，真正切屏）；**切屏动作由设备本地定时执行**，服务端只下发时刻不实时推送。
- **为什么不在 switch_at 时刻由服务端推 SWITCH_CONTENT**：推送依赖网络与服务存活，差一秒就是黑屏或迟切；本地定时是"提前拿到指令、到点自己动手"，断网也不影响已排定的切换。
- **放弃的备选**：纯实时推送（简单但把可用性绑死在网络上）；设备端自己算时刻（时区/DST 计算下放，错误面扩大）。

### D7 · 四态状态机 + FALLBACK 是 P0，"绝不黑屏"是底线

- **决策**：IDLE / MEETING_PREP / MEETING / FALLBACK 四态全做；预拉取失败重试 1 次仍失败 → 转 FALLBACK（保持旧内容 + 离线角标）；服务不可达 App 不退出，恢复当秒重连。
- **为什么 MEETING_PREP 故意不切屏**：先拉完再切，黑屏窗口 = 0；先切后拉会让"网慢"直接变成"黑屏几十秒"。
- **demo→生产的差异**：demo 只保证正向场景，FALLBACK/断网自愈在生产版升 P0——会议室屏黑屏是事故，不是瑕疵。

### D8 · 设备通信选长轮询，不选 WebSocket / MQTT

- **决策**：设备主动 `POST /api/device/poll`（hold 25s）+ 心跳 30s；服务端用 Redis pub/sub 唤醒 hold 中的连接补实时性。
- **为什么**：会议室网络**只出不进**（NAT/防火墙），服务器不能反连设备；长轮询是 HTTP 单向出站，穿透性最好；实现与排错成本最低。
- **放弃的备选**：WebSocket（要处理断线重连/心跳双套，穿透差）；MQTT（多一个 broker 运维面）。

### D9 · 指令幂等与防篡改：command_id + checksum

- **决策**：command_id 是幂等键（重复收到只执行一次）；checksum = sha256(command_id + payload 原文)，设备端可校验指令未被篡改。
- **为什么**：长轮询"至少一次"语义下重复下发不可避免，幂等键是正确性底线；checksum 让"指令被中间层改了参数"可被发现。

## C 组 · 日历与 M365

### D10 · 认证通道三选一、互不混用：JWT / X-Device-Key / URL token

- **决策**：管理端 JWT（8h）、设备端静态密钥头（绑定时配置）、免登录上传 URL token——三条通道独立校验。
- **为什么设备不走 JWT**：设备无人工登录能力，长生命周期凭据 + 密钥反查身份最简；为什么免登录页不走账号：定会者是外部角色，为传一张图建账号体系是本末倒置。
- **放弃的备选**：统一 OAuth（过度设计）；设备 JWT + 刷新（轮换复杂度无收益）。

### D11 · M365 用 app-only 服务账号（Application 权限），不用委托权限

- **决策**：Azure AD 应用注册 + `Calendars.Read` + `Mail.Send`（application 权限 + 管理员同意），服务端以 client_credentials 统一轮询所有房间邮箱。
- **为什么**：无人值守定时任务拿不到"某个用户的登录态"；一个服务账号管全部房间，**定会者零授权零感知**。
- **放弃的备选**：Delegated 权限（每次 token 绑定某用户，用户离职/改密即断）；每个房间单独凭据（管理爆炸）。
- **边界**：application 权限是租户级的（能读所有邮箱），最小化靠"只读房间日历 + 不申请 ReadWrite"约束。

### D12 · 日历只读，上传链接走邮件单通道

- **决策**：权限只申请 `Calendars.Read` + `Mail.Send`，**明确不加 Calendars.ReadWrite**；上传链接 = 邮件正文里的 URL，不做应用内消息/短信通道。
- **为什么**：只读 = 服务端永远不可能改坏客户日历（客户 IT 最关心的红线）；邮件单通道 = 一条依赖链好排错。
- **踩坑沉淀**：上传截止（会前 30 分钟）已过的会议**不发链接**——发了点开就是 2006，等于发废信。

### D13 · 免登录 token 三重约束：绑 meeting_id + 会后失效 + max_uses

- **决策**：token 绑定单场会议；expire_at = 会后；max_uses 默认 50；接口侧另校验上传截止 = 会前 30 分钟。
- **为什么双层时间**：expire_at 管"这场会结束了别再传"，截止校验管"会都开了 20 分钟传进来设备已经不拉了"——两个失效点语义不同，缺一就是漏洞或废数据。

### D14 · 多时区：全程 UTC 存储 + IANA 本地化，DST 交给 tzdata

- **决策**：DB 全 UTC；渲染按会议室 IANA 时区换算；美欧 DST 切换日与两段"错位窗口"（6h→5/7h）专项测试。
- **为什么不用"存本地时间+偏移量"**：DST 让固定偏移量必错；IANA 名 + tzdata 是唯一能自动处理历史/未来规则变更的方案。
- **验收锚点**：纽约的下午不能因为服务器在上海显示成夜间标牌（时段标牌按会议室本地小时选）。

## D 组 · Agent 与内容（LLM 可降级是红线）

### D15 · 降级链顺序固定：敏感判定 → CrewAI → 模板，6 秒超时即降

- **决策**：内容生成三层——**敏感判定最先且不用 LLM**（黑名单硬规则）→ CrewAI 生成 → 失败/超时（6s）降纯文字模板；`minimal` 版式只归敏感会议硬规则，Agent 候选集只有 standard/focus。
- **为什么敏感判定必须前置**：LLM 不可信，把"要不要脱敏"交给它 = 把合规交给它；黑名单命中后连 LLM 都不进，任何路径（含降级）只显示"会议中"。
- **踩坑沉淀**：demo 期模型曾把普通会议选成 minimal（敏感专用版式）——版式候选集收窄后修复。**Agent 的自由度必须用候选集硬约束，不能靠 prompt 求它**。

### D16 · 内容审核（F5.6）：预览/编辑留痕，RAG 命中可溯源

- **决策**：`GET/PUT /api/admin/contents/{meeting_id}`——管理员下发前预览与编辑；status 枚举 `generated / edited / template`；`kb_chunks_used` 记录 RAG 命中的知识库分块；敏感会议编辑**不允许改回真实标题**（1003）。
- **为什么留 kb_chunks_used**：文案错了要能回答"哪条知识垫进去的"——RAG 可溯源是审计底线。
- **为什么敏感会议禁止编辑标题**：审核入口不能变成泄露入口。

### D17 · initiated_by 审计必埋，新增 crewai:<agent> 枚举

- **决策**：全部指令与关键操作携带 initiated_by，枚举：`admin:<uid>` / `system` / `meeting:<mid>` / `organizer:<email>` / `device_user:<did>` / `crewai:<agent>`。
- **为什么**："这条指令谁发的"是运维排查第一问；Agent 产出被下发时留痕，LLM 行为才有追责链。

## E 组 · RAG 与检索（Milvus）

### D18 · RAG 双链路 P0：素材语义检索 + 品牌知识库，混合排序不用纯向量

- **决策**：①素材语义检索（"找科技感背景图"）= Milvus 向量 topK + 关键词/标签过滤**融合排序**；②品牌知识库（MinerU 解析分块入库）= Agent A 生成文案前检索 top3 垫 prompt。
- **为什么混合**：纯向量对"品牌色必须白色"这类硬条件无能为力；关键词/标签是精确过滤，向量是模糊语义，两者各管一半。
- **为什么知识库 RAG 升 P0**：文案要有企业调性，靠 prompt 硬写不如检索真实语料垫底——这也是与竞品差异化的核心点之一。
- **范围约束**：检索一期仅 `scope=public`；专属素材不经检索下发（按 meeting 直达）。

### D19 · 素材入库自动生成语义描述， Milvus collection 两分

- **决策**：上传时 LLM 依据文件名/分类自动补语义描述再向量化；collections 固定两个：`material_vectors` / `brand_kb`，schema 分开、`output_fields` 分别指定。
- **为什么文件名直接向量化不够**：`IMG_2043.png` 没有语义；描述是检索质量的源头。
- **踩坑沉淀（来自 PrismEdu 同型项目）**：Milvus 对 schema 外字段直接报错，output_fields 不搞通用大而全列表；collection 建库必须 load 才能search。

## F 组 · 设备端（一期 macOS）

### D20 · 一期设备端 = macOS 原生 Swift，Android 二期换壳

- **决策**：一期只交付 macOS App（Swift 6 + WKWebView + AVPlayer + LaunchAgent）；协议与状态机与平台无关，二期 Android 换壳（WebView/Media3/WorkManager/Room/BOOT_COMPLETED）。
- **为什么先 macOS**：Mac 本机 `swiftc` 直接编译运行即测，验证的是**协议与状态机**（项目最难部分）；Android 需要 JDK17 + SDK + 真机，门槛全在"壳"上。壳可以后补，协议错了才致命。
- **放弃的备选**：一期直接 Android（PRD 原案，因真机门槛推迟）；Flutter 跨端（会议室屏场景原生能力 > 跨端收益）。

### D21 · 设备本地缓存：15 天 LRU + checksum 校验 + 清理跳目录

- **决策**：素材落 `~/Library/Application Support/MeetCastDevice/cache`，sha256 校验（大文件首尾采样），15 天 LRU 清理；清理遇子目录跳过。
- **踩坑沉淀**：demo 期清理逻辑曾把**页面缓存目录**当素材删掉（日志实锤"清理清单外文件：pages"）——页面缓存迁独立目录 + 清理遇目录跳过。**清理逻辑必须白名单化，不能反向"删掉不在名单里的"**。

### D22 · 兜底页必须带重试，"正在重试"不许是谎话

- **决策**：WebDisplay 加载失败 → 缓存页 → 兜底页，兜底页带 20s 循环重试定时器，成功即停。
- **踩坑沉淀**：demo 期兜底页显示"正在重试"但没有任何重试逻辑——UI 承诺与行为不一致是最伤信任的 bug。**文案承诺什么，代码就得干什么**。

## G 组 · 安全与工程

### D23 · 密码 PBKDF2-HMAC-SHA256 12 万次 + 每用户独立盐

- **决策**：自实现 PBKDF2（纯标准库 hashlib），迭代 12 万次；登录失败统一报"邮箱或密码错误"（防账号枚举）。
- **为什么不用 bcrypt**：demo 期零依赖原则（纯标准库），生产 M1 可评估换 bcrypt/argon2——**换库时同步评审，不是现在**。
- **为什么迭代 12 万**：OWASP 2023+ 推荐 SHA-256 PBKDF2 ≥ 60 万（高危场景），12 万是"演示期可用、M1 前必须重评"的已知债务（诚实记录，M1 处理）。

### D24 · 配置单点：settings.py 唯一入口 + .env 不入库

- **决策**：所有配置（提前量/配额/密钥/开关/Graph 凭据）只在 settings.py 读取；敏感值只存 server/.env（gitignore）；`MEETCAST_` 前缀优先，兼容通用键名。
- **为什么**：散落的 `os.environ.get` 是配置漂移源头；.env 进 git 是凭据泄露最常见路径。

### D25 · 错误码分段语义：2013"本体已保存仅向量缺失"

- **决策**：v1.0 新增 2012（文档不存在）/ 2013（向量化失败）；2013 的语义设计为**部分成功**——素材/文档本体已落库，仅向量缺失，可重试补。
- **为什么不为向量化失败返回 5000**：5000 意味着重传文件，用户会为"搜不到"重传 500MB——错。错误码要表达"用户下一步该干什么"。

## H 组 · 路线（M0~M7）

### D26 · 第一刀切 PG 生产化（M1），不先做 Agent/RAG 花活

- **决策**：里程碑顺序 M0 规范 → M1 PG/Redis/登录骨架 → M2 macOS 设备端 → M3 M365 真接入 → M4 Agent 编排 → M5 RAG → M6 审核/加固 → M7 试点。
- **为什么 M1 最先**：持久化是所有功能的地基；地基不稳，LangGraph 的 checkpointer、审计、素材生命周期全都悬空。
- **为什么 M365 真接入排在 Agent 前**：日历是真数据源，没有真日历，Agent 编排测试全是假数据自嗨。

### D27 · 指令队列以 PG 表为准 + command_id 幂等 + Redis 锁单实例调度

- **决策**：command 表是队列唯一事实源；幂等靠 command_id；多实例部署时调度图由 Redis 分布式锁保证单实例执行。
- **为什么三者缺一不可**：只幂等不锁 → 邮件重复发（邮件无幂等键）；只锁不幂等 → 锁失效瞬间重复入队；只锁只幂等但队列在 Redis → Redis 挂 = 队列丢。三层正交防御。
